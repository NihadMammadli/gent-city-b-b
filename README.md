# Gent City B&B

Website for **Gent City B&B**, a boutique bed and breakfast at Notarisstraat 31
in Ghent's historic centre, managed by Damla Group.

**Live:** https://nihadmammadli.github.io/gent-city-b-b/

Next.js (App Router) + TypeScript, exported as static files. The look is the
Damla Group design system (damla-group.com); the structure follows
keraBrussels: every word, number and photo comes from one validated content
source, so nothing user-visible is hardcoded and the content can move to an
API without touching a component.

```bash
npm install
npm run dev            # http://localhost:3000
npm run build          # checks the content, then exports to out/
npm start              # serves out/ on :3000
npm run typecheck
npm run content:check  # validates the content (file or API) on its own
npm run images         # re-cuts the photos (see Images)
```

## Pages

| Path | What it is |
|---|---|
| `/` | Hero, welcome, guest scores, rooms, amenities, photos, location, hosts, reviews, FAQ |
| `/rooms/` | Both rooms side by side, and what every room includes |
| `/rooms/<slug>/` | One page per room in the content: description, facilities, photos, booking |
| `/gallery/` | Every photo, filterable, with a full-screen viewer |
| `/location/` | The neighbourhood, distances, and a map that loads on request |
| `/good-to-know/` | House rules, FAQ, languages |

A room added to the content gets its own page, sitemap entry and structured
data on the next build.

## Project structure

```
app/                  routes, metadata files (sitemap, robots, manifest, icons), globals.css
components/           one component per file, each with its CSS module
content/
  schema.ts           the content contract — what any source must provide
  site.json           the content today
  load.ts             picks the source (file or API) and validates it
  sources/            file.ts, api.ts
  index.ts            getContent() and lookups (photos, rooms, links, ratings)
  images.json         generated by `npm run images`
lib/                  paths (base path, absolute URLs), seo (metadata, JSON-LD), text helpers
scripts/              content-check.ts, images.mjs + images.config.mjs, brand.mjs
public/img, og, icons generated images
```

## Content

**No user-visible string belongs in `app/` or `components/`.** Pages call
`await getContent()` and pass what each component needs as props; components
never read content themselves.

### The contract

[`content/schema.ts`](content/schema.ts) describes the whole document with
Zod: the brand, the property, contact, rating, rooms, photos, reviews, places,
rules, FAQ, every page's sections and every UI label. The TypeScript types
come from it, and it also checks what a shape cannot: that every photo id,
room slug, gallery category, place and rating metric referred to exists.

Content that does not match stops the build with a list of exactly what is
wrong:

```
✗ The content from https://api.example.com/sites/gent-city-bb does not match content/schema.ts:
✖ no photo with the id "no-such-photo"
  → at rooms[0].cover
✖ "kitchen" is not one of the gallery categories: bedroom, living, bathroom, details
  → at photos[3].category
```

### Conventions

- **Empty means left out.** Clear a field and that part of the page is not
  drawn (the phone, email and WhatsApp are empty today, so they do not show).
- **`*stars*`** in a heading set those words in the bronze accent.
- **A blank line** in long text starts a new paragraph.
- **`{placeholders}`** in `ui` labels are filled by the page: `"Up to {n}"`.
- **Links** are a site path (`/rooms/`), an anchor, a full URL (opens in a new
  tab), or `@booking` — the booking page in `contact.bookingUrl`.
- **Icons** are named (`"wifi"`, `"fireplace"` … see `components/Icon.tsx`);
  an unknown name draws a check mark instead of a gap.
- **Photos** are referred to by id everywhere.

### Moving the content to an API

Set `CONTENT_API_URL` and the build reads the content from there instead of
`content/site.json`:

```bash
CONTENT_API_URL=https://api.damla-group.com/sites/gent-city-bb \
CONTENT_API_TOKEN=… npm run build      # token optional, sent as a Bearer header
```

The endpoint returns one JSON document of the same shape as `content/site.json`
— that file is the reference response. It is validated exactly like the file.
Photos the API hosts itself carry a `src` (plus `width`/`height`) and are drawn
as given; photos with a local cut use the responsive files.

The site is static, so new content is published by rebuilding. In CI, set the
repository variable `CONTENT_API_URL` (and the secret `CONTENT_API_TOKEN`); the
API can trigger a rebuild with a webhook:

```bash
curl -X POST -H "Authorization: Bearer <token with repo scope>" \
  https://api.github.com/repos/NihadMammadli/gent-city-b-b/dispatches \
  -d '{"event_type":"content-updated"}'
```

To swap the source for something else entirely (a CMS SDK, a database), change
`content/load.ts`; nothing else reads the source.

### Adding a field

1. Add it to `content/schema.ts` (and to `content/site.json`).
2. Read it in the page and pass it to the component.

TypeScript will not let a component read a field the schema does not promise.

## Images

The photos are the property's own, from its Booking.com listing.

```bash
npm run images
```

[`scripts/images.config.mjs`](scripts/images.config.mjs) lists each photo: its
id (also the file name, so it describes the picture), its original, the point
of focus a cropping frame must keep, and whether it is used full-width (`hero`,
also cut at 2400px) or as a share card (`og`). The script downloads originals
once into `.cache/originals/` (not committed) and writes:

- `public/img/<id>-<width>.webp` at 480, 800, 1200 and 1600px (and 2400 for heroes)
- `public/og/<id>.jpg`, 1200 × 630 share cards
- `content/images.json`: widths, shape, focus and a 24px blurred placeholder
- the icons: `app/icon.svg`, `app/apple-icon.png`, `public/icons/*.png`

`Picture` builds `srcset` from the manifest, so a phone downloads the 480px
file. To add a photo: add a recipe, run the script, add the photo (id, alt,
category) to the content.

## SEO

- Per-page title, description, canonical, Open Graph and Twitter card, from
  each page's `seo` in the content (`lib/seo.ts`).
- Structured data: `BedAndBreakfast` with address, geo, check-in/out,
  languages, amenities and each room as a `HotelRoom` (home); `HotelRoom` and
  `BreadcrumbList` on room pages; `FAQPage` on Good to Know.
  **There is deliberately no `aggregateRating`:** the scores come from
  Booking.com, and Google's rules forbid marking up ratings collected on
  another site. The rating is shown on the page, credited to its source.
- `sitemap.xml` lists every page with the photos it shows; `robots.txt`;
  a web app manifest and icons.
- One `h1` per page, descriptive `alt` on every photo, width and height on
  every image, the hero fetched first.

On GitHub Pages the site lives under `/gent-city-b-b`, where search engines do
not read `robots.txt`; it takes effect once the site has its own domain.

## Design

The Damla Group system, carried over from damla-group.com:

- **Urbanist** throughout; large light headings (400), grey body copy.
- **Navy** `#0F1729` ink and footer, **slate** `#343D52` header, **bronze**
  `#9C6D36` for every action, **gold** `#D4AF37` for fine detail only — icon
  rings, the offset frame behind photos, rules and active dots.
- Fields alternate white, light `#F5F3F0` and cream `#E8E0D5`.
- Full-bleed hero under a navy gradient, the blurred placeholder showing until
  the photo arrives, title and buttons rising in one after another.
- Sections fade up as they are reached; image and text slide in from opposite
  sides; scores count up.

**The page renders finished in CSS.** A two-line script in `<head>` adds a
`motion` class only when the visitor has not asked for reduced motion, and
only that class hides anything before it animates in; it removes itself after
three seconds if the JavaScript never arrives. Do not hide content anywhere
else. The FAQ works without JavaScript, the review row and gallery scroll
natively, and the map only contacts OpenStreetMap when asked.

## Deploying

`.github/workflows/deploy.yml` typechecks, checks the content, builds and
publishes `out/` to GitHub Pages on every push to `main` (pull requests build
without publishing). The base path and origin come from the Pages settings, so
a custom domain needs no code change: add it in *Settings → Pages* and the next
build uses it for canonicals, share cards and the sitemap.

```bash
gh workflow run deploy.yml     # publish again without a commit
```

The export is plain files and runs anywhere that serves a folder (it can sit
beside KERA on the Hetzner server behind Traefik in the same way).

## Content notes

Facts come from the Booking.com listing (fetched 2 November 2026) and the
hosts' own texts there. Worth confirming with the hosts:

- Booking.com lists quiet hours as 07:00–22:00; the site says **22:00–07:00**,
  which is what was surely meant.
- The **Stairs** rule is drawn from guest reviews (steep stairs, unsuitable for
  reduced mobility), not from the listing.
- **Phone, email and WhatsApp** are not on the listing and are left empty.
- **Reviews** are quoted from Booking.com with spelling and capitalisation
  tidied; reviews that mention perks not on offer (e.g. breakfast) were left out.
- The listing gives no breakfast details, so the site makes no breakfast claim.
